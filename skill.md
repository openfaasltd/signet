# Signet

Signet is a lightweight OpenID Connect provider for agents and automation. It
stands in for a full IdP (Keycloak, Auth0) in demos, integration tests, and
single-node clusters. It is deliberately small: ES256, two grants, no refresh
tokens. It is a development/demo identity provider — do not use it for
production credentials.

## Endpoints

| Path | Purpose |
|------|---------|
| `/.well-known/openid-configuration` | OIDC discovery |
| `/.well-known/jwks.json` | JWKS (ES256, kid `signet-1`) |
| `/authorize` | Authorization endpoint (login page on GET, code on POST) |
| `/token` | Token endpoint |
| `/healthz` | Liveness |

Discovery is the source of truth for `authorization_endpoint`,
`token_endpoint`, and `jwks_uri` — all derived from the single `issuer` value.
The `issuer` must be byte-identical everywhere it is consumed (see
"Consistency" below).

## Grants

- **`authorization_code` + PKCE (S256)** — the human opt-in path. A browser
  hits `/authorize`, logs in with username + password, gets redirected back
  with a code, which is exchanged at `/token`. Used by the OpenFaaS dashboard
  and `faas-cli pro auth` (interactive).
- **`client_credentials`** — the machine/agent path. No browser, no PKCE.
  `POST /token` with `client_id` + `client_secret` returns a signed JWT
  directly. Used by CI and agents. The client must have a `secret` and a
  `subject` configured.

Both return the same JWT as `access_token` and `id_token`. The JWT carries
`iss`, `sub`, `aud` (array), `iat`, `exp` (1h), and `groups`.

## Client types

- **Confidential** — has a `secret`. Used by the dashboard (`openfaas`) and by
  `client_credentials` machines. The token endpoint checks the secret.
- **Public** — no `secret`. Proves possession via PKCE only. The code grant
  must not require a secret for public clients, or the interactive CLI breaks
  (its callback posts `client_id` + `code_verifier`, never a secret).

## Provisioning

### v0 — config file (what works today)

Users and clients live in a static `config.json` (mounted from a k8s Secret in
cluster). To change them:

1. Edit the config (add a user or client).
2. `kubectl rollout restart deployment/signet -n openfaas` — signet loads
   config at startup and has **no hot-reload**.
3. Verify the change is live by probing `/authorize` with the new
   `client_id` (expect 200, not 400).

Passwords and secrets are written into the config by hand or generated by the
operator. There is no admin API, no CLI, no state dir, and no bootstrap token
in v0.

### Target — admin API + CLI (the UX to build)

The provisioning UX should be agent-drivable, not "edit a Secret and restart."
The target surface, gated by a management Bearer token:

- `POST /admin/users` `{username, groups[], password?}` → `201 {username, password}`
  — password is **generated** (crypto/rand) and returned **once** if not supplied.
- `GET /admin/users` → list (never returns passwords).
- `PATCH /admin/users/{name}` `{groups?, password?}`.
- `DELETE /admin/users/{name}`.
- `POST /admin/clients` `{id, redirect_urls[], secret?}` → `201 {id, secret}`
  — secret generated and returned once if not supplied.
- `GET /admin/clients`, `DELETE /admin/clients/{id}`.

A thin CLI wraps this (mirrors the slicer daemon-plus-CLI pattern):

```
signet user add han --groups admin          # prints generated password once
signet user list
signet user rm han
signet client add ci --redirect-url URL     # prints generated secret once
signet client list
signet client rm ci
```

Flags: `--url`, `--token` (and `--token-file`).

### Bootstrap / seed admin

On first start (empty state), signet should generate the signing key, generate
a management token, create a seed admin user, and print the token + admin
password **once** to stdout. For deterministic e2e, allow `--admin-token` and
`--admin-password` flags (or env) so a test knows them without scraping logs.
This mirrors slicer's Bearer-token-from-file model.

### State dir

Move from a static file to a state dir (default `./signet-state`, override
`--state-dir`) holding `signet.key`, `users.json`, `clients.json`, and the
admin token. Admin-API mutations persist there (atomic write: tmp + rename).
The static `config.json` becomes an optional seed imported only on first start.
In Kubernetes, mount this state at `/var/lib/signet` from the `signet-state`
`ReadWriteOnce` `local-path` PVC. The signing key then survives pod restarts
and rollout replacement on the node. For multi-node deployments, replace it
with an appropriate network-backed PVC.

## Credential handling rules

- **Generate by default.** Never ask a human to invent a password or secret;
  generate with crypto/rand and return it once.
- **Return once.** The generated password/secret appears in the create
  response (or the one-time bootstrap print) and is never returned again.
- **Protected files, not chat.** When a credential must be shared, write it to
  a `chmod 600` file and pass the **path**, not the value. Never put a secret
  in retained mail, a commit, or a log line.
- **Encryption at rest (optional).** Plaintext at rest is acceptable for a
  dev/demo IdP **only** because it is not for production. To harden, run with a
  32-byte AES-256 master key (a plain file; in Kubernetes a Secret mounted at
  a path). With a master key present, `config.json`, `signet.key`, and
  `admin-token` are stored as AES-256-GCM envelopes (`SIGNET-SEALED-v1`).
  Without one they stay plaintext (0600, UNIX perms). The master key is never
  written to the state dir, so a volume-only exfiltration (backup, snapshot,
  image layer) yields ciphertext. It does **not** protect against an attacker
  who can read both the master key file and the state volume.
- **Master key is a file, never an env var.** The Helm chart
  (`chart/signet`) generates a random master key on install (or honours
  `.Values.masterKey`), ships it as a Kubernetes Secret, mounts it as a file,
  and passes the path via `--master-key-file`. It is kept across upgrades
  (`helm.sh/resource-policy: keep`) and survives uninstall.

## Consistency — the thing that breaks the demo

The `issuer` URL must be **byte-identical** in every place that consumes it:

1. signet's own config (`issuer`),
2. the dashboard's `primary_issuer`,
3. the oidc-plugin `systemIssuer.url` and `dashboardIssuer.url` (the helm
   `--set` values),
4. the `JwtIssuer` CRD's `iss`.

The oidc-plugin does an **exact string match** on `iss` and checks `aud`
against the `JwtIssuer` CRD's audience list. A mismatch (e.g. in-cluster
`http://signet.openfaas.svc:8080` vs the external tunnel URL) silently fails
the token exchange. Derive the issuer once and inject it into all consumers.

Likewise the dashboard's `redirect_uri` (its `public_url` +
`<BaseName>/auth/callback`) must be registered **exactly** in signet's client
`redirect_urls` — the match is `==`, not a prefix.

## The two-sided change (rename / add a user)

Adding or renaming a user is a **two-sided** change. Both must move together:

1. The **IdP subject** — the signet user's `subject` (defaults to username).
2. The **Role principal** — the oidc-plugin `Role` CRD's
   `spec.principal["jwt:sub"]` list.

If only one moves, the subject matches no role, the oidc-plugin finds no
policy, the dashboard's id_token exchange fails, and the user sees
"Not authorised." This bit us: renaming `demo` → `openfaas` updated the signet
subject but left the Role principal as `[demo, …]`.

## Verification gates (do not skip)

After **any** Policy / Role / JwtIssuer CRD change, do **not** assume it is
live. The faas-netes informers can miss an update and serve stale authz.
Verify the consuming component actually reloaded it:

- oidc-plugin: `kubectl logs <oidc-plugin pod> | grep -E 'Updating (Role|Policy|issuer)'`
- operator (gateway sidecar): `kubectl logs <gateway pod> -c operator | grep 'Updating policy'`

If the reload is absent, force a no-op spec update (e.g. a `kubectl patch`
that adds then removes an action) and re-verify. A read that 200s and a write
that 403s is the signature of a stale policy cache.

With the `signet-state` PVC mounted, a Signet restart retains `signet.key`.
The public JWKS and existing signed tokens remain valid, so the dashboard and
oidc-plugin do not need restarting after a Signet rollout. Treat loss of the
PVC as a deliberate key rotation and verify consumers have refreshed JWKS.

## Known issues

- **No hot-reload.** Config changes require a pod restart.
- **`access_token` == `id_token`.** Same JWT for both. Fine for a demo; a real
  access token would differ.
- **No refresh tokens.** (See Target below.)
